# 06. 개발 로드맵

> 3단계 Phase로 나누어 개발한다. 각 Phase는 독립적으로 가치를 제공하며(수기 운영 → 첫 채널 자동화 → 멀티채널·정산), 앞 Phase의 검증 결과가 다음 Phase의 선행조건이 된다.

---

## Phase 1 — MVP: 공급자 운영 기반 (직판·수기 채널)

**목표**: 공급자가 상품·재고·예약을 시스템으로 관리하고, 현장에서 리딤까지 가능한 최소 운영 시스템. 채널 연동 없이 수기(전화·메신저·직판) 예약으로 운영 검증.

### 범위

| 모듈 | 포함 | 제외 (후순위) |
|---|---|---|
| 사용자/권한 | 공급자 가입·심사·승인, 역할 4종, 멀티테넌시, 이메일 인증 | 2FA, SSO |
| 상품 | 카테고리 C1(입장권)·C2(투어)·C3(액티비티) 우선, Product→Option→Unit 등록, 취소정책 3유형, 동적 예약필드 | C8 패키지, 좌석등급(C4 상세), Add-on |
| 가격 | 기본가 + 시즌/요일 오버라이드, 가격 캘린더 | 인원구간 계단가, 채널별 가격(채널 없음), 프로모션 |
| 재고 | 3유형(타임슬롯/일자/오픈데이트), 스케줄 템플릿→슬롯 생성 배치, 재고 캘린더, 블록아웃, 원자적 차감·홀드 만료 | 채널 allotment |
| 예약 | 수기 예약 등록, 상태머신 전체, 수동 확정(PENDING 큐), 수정·취소(환불액 자동 계산), 감사 로그 | 채널 유입 |
| 바우처/리딤 | 발권(QR/코드/PDF), 이메일 발송, 현장 모바일 리딤(스캔/입력), 노쇼 배치 | 패스형 복수 리딤 |
| 리포트 | 기본 대시보드(오늘 예약/이용/확정 대기), 예약 목록 내보내기 | 정산 |

### 선행조건·산출물
- 선행: 본 설계 문서 승인, 기술 스택 확정, 파일럿 공급자 1~2사 섭외
- 산출: 어드민 웹 + 현장 모바일 웹, 파일럿 공급자 실운영 검증

### 리스크
- **재고 모델 추상화 실패** 시 이후 전면 재작업 → Phase 1에서 3유형 모두 실상품으로 검증할 것
- 카테고리별 동적 필드의 과설계 주의 — 파일럿 상품에 필요한 필드만 스키마화

## Phase 2 — 첫 채널 연동: OCTO API 서버 + Klook

**목표**: OCTO 표준 API 서버를 구축하고 첫 PULL형 채널(Klook)을 연동. 채널 예약이 자동으로 유입·확정·발권되는 파이프라인 완성.

### 범위

| 항목 | 내용 |
|---|---|
| 채널 게이트웨이 | OCTO API 서버 (products / availability calendar·check / bookings 2단계 커밋), API 키 관리, rate limit, 멱등성 |
| Capability | `octo/pricing` (3중가), `octo/content` |
| 채널 관리 | Channel·매핑 CRUD, 채널별 커미션·가격 설정(고정가/할인율), 동기화 모니터링 화면 |
| 재고 이벤트 | 매진/재개 도메인 이벤트 → 채널 통보(webhook 준비, Klook pull 주기 보완) |
| 예약 파이프라인 | 채널 예약 유입 → 온리퀘스트 확정 전파 → 발권 정보 응답 → 취소 수신 |
| 가격 확장 | 채널별 가격(PriceRule.channel_id), 인원구간 계단가 |
| C4·C5 카테고리 | 공연(등급별 수량제)·교통(온리퀘스트 배차) 지원 확장 |

### 선행조건·산출물
- 선행: Phase 1 실운영 안정화(오버부킹 0 검증), **Klook 파트너 계약 및 연동 인증(certification) 절차 진행** — 계약·심사 리드타임이 길 수 있으므로 Phase 1 중 병행 착수
- 산출: Klook 실판매 상품, 연동 운영 절차(장애 대응 런북)

### 리스크
- 채널 인증 심사 지연 → 조기 착수, OCTO 표준 준수로 심사 리스크 최소화
- 게이트웨이 장애 = 채널 상품 자동 비활성화 위험 → 게이트웨이 이중화·모니터링을 이 Phase에서 필수 구축

## Phase 3 — 멀티채널 + 정산/리포트

**목표**: GYG(PULL)·KKday/Trip.com(PUSH) 어댑터 추가로 멀티채널 판매 체계 완성, 정산 자동화.

### 범위

| 항목 | 내용 |
|---|---|
| GYG 연동 | GYG Supplier API 스펙 구현(reserve/book/cancel, notify push), PRODUCT_DEACTIVATION 대응 플로 |
| KKday/Trip.com 어댑터 | PUSH 어댑터 프레임(재고 push·예약 웹훅 수신·재시도 큐), 파트너 계약 후 채널별 스펙 반영 |
| 채널 allotment | 채널별 재고 배정 (공유재고 기본 + 보장 수량 옵션) |
| 정산 | 월 정산 배치(완료 예약 집계·커미션 공제), 정산 검토·확정·조정, 채널 대사(reconciliation) 배치 |
| 리포트 | 채널별·상품별 판매 분석, 취소율·리드타임, CSV |
| C8 패키지 | 정적 번들(구성 재고 원자 차감), 선택형 패스(복수 리딤)는 후순위 |
| 운영 고도화 | 딜/프로모션, 대량 작업, 다국어 콘텐츠(영문) |

### 선행조건·산출물
- 선행: Phase 2 안정 운영, GYG·KKday·Trip.com 파트너 계약 (KKday 인바운드 API는 비공개 — 계약 후 스펙 수령 필요, 미확보 시 채널매니저 경유안 검토)
- 산출: 4채널 판매 + 월 자동 정산

### 리스크
- 채널별 비공개 스펙 의존 → 어댑터 인터페이스를 먼저 고정하고 채널 구현체만 교체 가능하게
- 정산 불일치 분쟁 → 예약 시점 가격 스냅샷·대사 배치로 방어

## 전체 일정 감각 (참고)

| Phase | 내용 | 상대 규모 |
|---|---|---|
| 1 | MVP (상품·재고·예약·리딤) | ★★★★ — 도메인 모델·재고 엔진이 최대 작업 |
| 2 | OCTO 서버 + Klook | ★★★ — 게이트웨이 신규 + 인증 절차 |
| 3 | 멀티채널 + 정산 | ★★★ — 어댑터 반복 + 정산 배치 |

> 절대 일정은 팀 규모 확정 후 산정. **채널 파트너 계약(Klook/GYG/KKday/Trip.com)은 기술 일정과 무관하게 리드타임이 길므로 Phase 1 시작과 동시에 병행 추진할 것.**
